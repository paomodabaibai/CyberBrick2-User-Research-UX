## 实际操作与观察（按时间顺序）

1. 接收板接 USB，第一次 `walk_session.run(20)`：strict enable 立即因“remote returned no valid frame”拒绝；程序打印 `PWM off`，没有进入行走。接收板 `rc_slave_init()` 后一次只读探针的第0帧是 `None`，后续数帧曾出现正常10通道数据，左右杆约1959/1782–1792、K4=1。这说明遥控链路**曾短暂可读**，并不证明后续持续可用。
2. 延迟500ms再试 `walk_session.run(20)`，仍在 enable 阶段因无有效帧拒绝；随后15次、25次间隔采样均为 `None`。
3. 为解决一根线换到发射板后无法从接收板串口启动的问题，新增并上传上面的 `battery_walk.py` 与 `main.py`。用户将 USB 从接收板换到发射板，接收板靠电池；两板指示灯均为绿色，用户认为正常时应为黄色。**灯色的含义尚未从官方资料核实，不能仅凭绿灯判定配对或数据收发成功。** K4 与摇杆均未引起动作。
4. 用户将 USB 换回接收板，发射板仍靠电池且亮灯。板上检查显示 `battery_walk` 模块已加载、`config.DRIVER='cb1_pwm'`；`rc_slave_init()` 返回 True，但连续15次遥控读取仍全部为 `None`。检查本身通过 `mpremote` 进入 REPL，会打断正在运行的程序，因此该检查之后要重启接收板才能重新运行 `main.py`。
5. 用户再将 USB 换到发射板。其 `boot.py` 存在，内容在上电后导入 `/app/rc_main` 并调用 `rc_main.main()`；GPIO10=1（发射角色），`rc_main` 可导入。此前用串口检查发射板可能打断了其官方发送程序，而电池持续供电使拔插 USB 不会自动重新执行 `boot.py`。据此执行 `machine.reset()`，启动输出包括 `HARD_RESET`、`MASTER_INIT`、`PARSE_UPDATE`、`AUTO_SLEEP_DIS`，证明**发射程序在这次重启时启动**。随后用户再次按说明重启接收板、尝试 K4 和左杆，现场反馈仍然**完全没反应**。
6. 最后一次试验没有同时抓到接收板启动日志/遥控帧，也未看到 `battery_walk` 的 arm/enable/状态打印。故目前不能判定卡在：发射没有持续送帧、接收没收帧、K4 手势未达门槛、`main.py` 冷启动异常、还是已进入 READY 但步态请求未触发。**也没有本夜任何新舵机动作证据。**

## 当前软件语义与需注意之处

- 正式 v02 步态已实现五阶段协同；左右杆前推 +1、回中解锁，双杆同时推为冲突；同侧连续重复步在 v02 被拒绝，先交替左右试。理论功能已过 PC 测试，不等于真实走路。
- `battery_walk.py` 的 K4 在**启动前**用“按住1秒后松开”手势使能；启动后 K4 恢复停止。停止/失联会结束这次入口并关 PWM，重试须重启接收板。试验窗口120秒。它没有视觉反馈；没有串口日志时，用户无法仅凭灯色确认是否使能。
- `mpremote resume exec/fs` 可进入板端 REPL，但通常会打断正运行的程序；在两板由电池持续供电时，仅拔插 USB 不能保证官方发射程序或 `main.py` 自动恢复。每次串口检查之后，下一次试走前必须明确重启被检查的板。接收板 `main.py` 自动运行这一点也意味着下次调试须先确认安全支撑和物理断电开关位置。
- 接收板原官方 `rc_config` 仍在，但原官方 `boot.py` 已禁用；它不应直接驱动舵机。发射板官方 `boot.py` 未改。
- S2/S3 先前“零反应”曾是插头接触不良，不能由今晚整体无响应直接推断舵机坏。若未来证实已发 PWM 而某单关节不动，再回到插头/供电检查。
