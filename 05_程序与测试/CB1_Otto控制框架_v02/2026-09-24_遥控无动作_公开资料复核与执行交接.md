- 官方舵机驱动：https://github.com/CyberBrick-Official/CyberBrick_Controller_Core/blob/master/src/app_rc/bbl/servos.py
- 官方启动入口：https://github.com/CyberBrick-Official/CyberBrick_Controller_Core/blob/master/src/app_rc/boot.py

确认事项：

1. rc_slave_init 初始化无线接收；rc_slave_data 返回 L1/L2/L3/R1/R2/R3/K1/K2/K3/K4。它不会根据我们的需求自动协调四条关节。原始遥控数据可用与动作程序正常是两个层次。
2. 官方 Python 启动脚本调用 rc_main.main；接收侧另外创建 BBL_Controller，再把遥控数据送给它。官方界面通道映射由这层处理，不是无线 API 自带的行为。
3. 官方舵机也是 machine.PWM，50Hz，S1–S4 对应 GPIO3/2/1/0；当前直驱方案在这些基本参数上相符，没有证据表明必须改用官方舵机类。
4. 官方 BBL_Controller 有 Timer(0) 周期回调、舵机插值，以及 BEHAVIOR/EVENT/EXEC 权限管理。App 代码片段还经过执行器映射。外部独立程序直接 PWM 不自动参与这套权限管理。如果同一运行环境还保留官方输出任务，存在覆盖风险。
5. 仅导入模块不等于后台控制正在运行。必须找到初始化/运行路径、实例和回调才能证实竞争；不能看到 control.py 或 rc_main 文件存在就认定它在抢占。
6. 当前自定义代码不使用官方 set_angle_stepping，因此“补调官方 timing_proc”不适用于我们，不能照搬。
7. 官方仓库 issue #6 曾记录板载 .mpy 与公开仓库版本不一致：https://github.com/CyberBrick-Official/CyberBrick_Controller_Core/issues/6 。因此公开源码说明机制，不证明板上固件精确相同；不要无依据升级或降级。

## 已确认的本地流程缺陷

这些是阅读文件即可确认的行为，并不等于已确认全部故障根因：

- battery_walk 是一次性会话：等待 K4 长按松开使能，开始后最长 120 秒；K4/失联终止会话并 finally 关 PWM，函数返回。不重启/重新调用就不会再次接受遥控。
- trace_remote_walk 默认 90 秒后退出；walk_session 也是定时入口。用户之后继续推杆没有动作是预期行为，界面却没有持续明确告诉用户是否还可控制。
- 起步门槛包括：回中、前推超过阈值、左右交替、忙时丢弃请求。同侧反复推和向后拉不会按用户直觉反复迈步。
- 这些限制不足以解释 trace 日志中已接受并完成的步态为何没有可见动作。不能靠降低阈值、缩短长按或取消安全门禁“修复”这一证据矛盾。
- 反复 resume/热导入是为了保留无线运行状态，但也使“当前是否有旧实例/旧回调”不透明。删除 sys.modules 不是清除已有实例或硬件回调的证明。

## 给下一位 Agent 的执行顺序（本轮不执行）

### A. 先做一次静态入口与输出所有权审计

利用已有备份和源码，列出两板各自 boot.py → main.py/rc_main → 工作循环的实际路径；将“文件已上传”“已导入”“正在持续运行”分开。记录两板固件、Python 应用版本，别混为一个版本。

接收板建议保留 rc_module 作为无线输入，四关节只由 cb1_pwm 一处输出。发射板先保持当前能发送有效数据的方案。不要重新配对，不重写无线协议，不修改步态参数。

查全部 PWM(Pin(...))、ServosController、BBL_Controller、Timer 初始化及 release/deinit 路径。若确有第二个舵机写入者，给出明确调用路径后清理。若干净上电从未初始化官方控制器，应排除该猜测，不继续归咎于官方抢占。

注意：本机历史接收板 boot 曾改名禁用，后来软件重配又清空过文件。必须以最新已保存内容为依据；历史描述不够时只列待核实项，不擅自猜当前状态。

### B. 修清楚产品运行生命周期，再恢复用户测试

规划一个唯一的正常遥控入口，和所有定时诊断入口分开。冷启动保持未使能；用户显式使能；K4 随时停止；失联停止；恢复仍需显式操作和回中。不要依靠“有帧即走”。

正常运行不能悄悄在 90/120 秒后结束。如果实验仍需超时，必须显示倒计时、超时原因和恢复方法。停止/故障后程序可以继续服务输入但不能自行恢复运动。定义清楚使能手势与停止按钮是否共用，提供等待、就绪、运动、停止、失联的可观察状态。

这部分是后续设计/实现任务，不是本轮已完成修复。先提出最小改动，保留原始代码备份与限位，勿大规模重构。

### C. 必要时只做一项小范围闭环验收，不再轮番跑长脚本

在明确唯一入口、唯一输出者后，由后续执行者安排：真实左杆触发一个已标定关节在安全范围内变化，回中后可重复；K4 停止。不要先接五阶段全身步态，不增加角度，也不取消保护。

如果软件接收并下发但仍无动作：再检查输出实际脉宽/频率与舵机端供电，必要时测量，不用更多状态日志替代物理输出。PWM getter 只是寄存器/对象层证据，不等于舵机接头有正确波形。

如果该闭环可靠，再接回现有步态并按“左推→左步、回中→右推→右步”确认。用用户确认/视频建立时间对应，软件 done 不算动作验收。通过之后再讨论同侧重复请求和连续走。

## 不应做的事

- 不把黄灯或 step done 当成机器人已遥控成功。
- 不继续凭上午猜测改 K4 去抖/长按阈值。
- 不盲目停所有 Timer、删除系统库、恢复出厂或升级固件。
- 不因存在社区 ESP-NOW 示例就整体替换当前已收到帧的链路。
- 不直接实例化官方 ServosController 做替代测试：它会初始化四个输出，必须先处理与现有 PWM 的所有权及限位。
- 不把尚未回复的自动步行对照观察写为成功或失败。
