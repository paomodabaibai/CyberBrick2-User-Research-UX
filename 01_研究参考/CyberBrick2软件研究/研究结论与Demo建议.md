# CyberBrick / CB2 软件研究与本周巴掌 Demo

日期：2026-09-17。研究对象：本机 CyberBrick 0.0.28-alpha.49.no-bluetooth.fix-company-models。依据是实际安装文件与实时 MCP 工具目录，不是泛化的 ESP32 教程。

## 结论

用户的判断正确：软件内置了硬件 API 知识库、系统提示词、接线模型、项目模板和执行工具。大模型通过这些资料理解 CyberBrick，再通过工具写文件、同步到板端、执行 MicroPython 并读回结果。这不等于模型天然了解每块实物，更不代表能自行知道舵机在机械结构中的用途。

- 知识库实际位于 `resources/app.asar.unpacked/src/main/ai-editor/knowledge`，以 Markdown、JSON、YAML、Python 等文件保存。

- 本次仅调用 initialize、tools/list、list_skills；没有调用设备 REPL、上传、运行、重置、Wi-Fi 设置或修改 CyberBrick 项目。
- 研究副本保存到本目录；含密钥形式的字符串已在文本副本中脱敏，安装程序保持不变。不要将完整程序研究副本直接公开分发。

## 它如何知道怎么写代码

1. **系统提示词**：`prompt/system-build/cb2.yaml` 组装身份、运行环境、项目空间、工作流程和代码规范。流程覆盖接线核对、固件版本匹配、先写文件再同步运行、多板区分、运行时控制等。
2. **按固件分版的文档**：`skill/cb2/cba-api-doc` 内实际有 00.00.00.01、00.00.01.00、00.00.10.00、00.00.10.19、00.00.10.37、00.00.10.70、00.00.10.76。软件要求根据项目/板端的 mpy 版本选文档。不能把应用版本当成固件版本。
3. **接线与组件模型**：`wiring.json` 记录板型、模块类型、连接器、引脚及启用状态；应用内还有 CB2Base 的连接器定义。模板只是样例，不是当前实物的接线证据。
4. **板端识别**：`cyberbrick.Port.list()` 提供 port_id、port_name、module_type、module_name 等信息。`auto_port.py` 按模块类型筛选，再按端口编号排序。
5. **工具执行闭环**：大模型生成项目文件，工具同步板端副本，然后运行并收集输出，模型据此继续调整。板端执行的是定制 MicroPython 与 CyberBrick SDK，不是完整桌面 Python。

典型流程：用户目标 → 系统提示词与 API 文档 → 项目接线/板端状态 → 生成代码 → 同步板端 → 执行 → 输出反馈。

## 关于组件识别，必须分清两件事

它能知道某端口是什么类型的模块；它不能由此知道“这个 Servo 是左髋还是右脚”。四个腿部舵机加一个巴掌舵机必须建立固定的用途—端口表。按排序取第几个 Servo 在换线后可能改变含义，不能直接把这个排序当成机械语义。

内置 auto_port 源码还明确写着：该实现的接线扫描发生在上电/软复位阶段，热插拔后不会自动刷新；auto_port.reset() 只清自身缓存，不能代替板端重新扫描。本次未在实机验证这一限制。

## 对巴掌 Demo 有用的已发现能力

以下来自打包的 **00.00.10.76 文档样本**，只用于能力研究，尚未选为我们实物的目标版本：

- Servo：角度模式、连续旋转模式、角度模式速度百分比、角度限位、实际角度反馈、零点校准。
- 这意味着“直接装舵机”依然可以研究不同挥掌和回位速度；不必先加弹簧。但实际速度、力矩、机械冲击和接口可用性仍要对实物核实。
- 新版样本文档采用 `cyberbrick.Servo(port=...)`；部分旧提示词还写 `from cba import ...` 或 `port_name`。这正说明不能抄任意网上示例，也不能混用不同版本的参数名。
- Port 与应用 CB2Base 定义包含 A1–A6、B1–B6 共 12 个命名端口。这是软件接口模型，不证明现有扩展板配置、电源能同时带五个舵机，更不代表十二路舵机同时带载能力。
- Wireless 文档提供 DCN 分组与标签发布/订阅，是遥控通信的候选基础。尚未验证你们手里的遥控器属于哪种硬件及如何配对。
- IMU 文档和板载 IMU 模型存在，可留作以后跌倒识别参考；本周首版不因此扩大范围。

## MCP 和软件内聊天的关系

外部 Agent 可以通过 MCP 读取内置知识并调用执行工具，不必局限于 CyberBrick 内部聊天界面。但外部 MCP 并不自动获得全部内置系统提示词，公开的工具也少于软件内部工具；例如此次公开清单未包含内部的 read_wiring / validate_wiring。

MCP 文件工具固定操作：
`C:/Users/Administrator/AppData/Roaming/CyberBrick/ai-editor/projects/mcp-project/project`

它与软件当前打开的普通项目不是同一个概念。我们的课程目录继续是资料、CAD、程序源文件和测试记录的主目录；未来上传前再明确映射到哪个 CyberBrick codebase、哪块 deviceId。不能误以为在课程文件夹改代码就已经同步到设备。

## 本周建议的最小 Demo 顺序

1. 确认实物：核心板、扩展板、舵机、遥控器、电池的型号/照片，读取实际固件版本；量舵机外壳、固定孔、输出轴与舵盘尺寸。
2. 单独巴掌样机：一个驱动＋短横臂＋软掌，实现“触发—挥掌—回位”，先在固定支架上验证。
3. 遥控链路：增加一个攻击按键，测试重复触发、松键与通信中断时的行为。
4. Otto 适配：保留腿部运动关系，局部改舵机座、舵盘连接、板仓、电池仓；先做小试片，不整体等比缩放模型。
5. 四腿部驱动逐个校准后，先站立，再短距离移动，最后合并巴掌；建立五路固定用途表。直驱巴掌暂按一舵机估算，不作为已采购事实。

当前尚缺实际器件尺寸、板端固件、接线与电源能力；软件文档无法替代这些信息。尚未找到足以证明套件机械尺寸的工程 CAD，不能依据 UI 图片改孔位。
